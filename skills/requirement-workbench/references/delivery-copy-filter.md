# 交付物文案与无痕改动

这是所有最终交付物的强制过滤器。用户可见的界面、原型、PDF、PPT、报告、截图、图表、HTML/SVG 和导出文件只服务产品或业务目标，内容必须像真实产品或真实业务材料。

## 交付物文案

- 不要把 agent 的思考过程、实现理由、设计推理、调试过程、下一步计划写进交付物。
- UI 中禁止出现「我将」「我们可以」「本页面用于展示」「这里会」「用于说明」「实现了」等解释型文案，除非它本来就是产品里的帮助文本、引导文案或空状态文案。
- 实现思路、验证方式、限制与取舍只写在聊天回复、代码注释、PR/MR 描述、技术文档或计划文件中，不要混进面向最终用户的产品内容。
- 用户明确要求交付物展示「设计说明」「方法论」「实现过程」或「工作记录」时，才把这些内容写入交付物，并按真实受众重新组织，不要直接复制 agent 自述。
- PRD、详细规格、审核报告、测试报告等文档可以保留其任务本来要求的规则、证据、风险、限制和待确认项；删除的是代理过程和无关解释，不是文档应有的专业内容。

## 无痕改动原则

- 除非代码安全、复杂逻辑、法规、兼容性或维护确有需要，改动后不添加注释、说明、标记或「为什么这样改」的痕迹。
- 不在页面角落、组件名、数据、样式类、文案、截图注释或导出文件里留下 `demo`、`mock`、`AI generated`、`这里修改了`、`新版` 等过程标记，除非它们是被确认的产品内容或测试标识。
- 复用项目原有的命名、结构、语言和设计系统。结果应当像项目本来就这样，而不是在旧内容外面包一层补丁。
- 改动原因和验证证据放在聊天交付说明、代码评审、PR/MR 或专门记录中。不要为了“无痕”删除需求追踪、审计记录、许可证、安全说明或其他必须保留的信息。

## 提交流程

- 提交信息必须准确反映最终交付结果，不写排查过程、试错过程或没有进入交付物的中间方案。
- 提交前确认实际 diff 与提交信息一致；不要声称已经验证、上线、兼容或完成业务结果，除非有对应证据。

## 强制过滤

生成前先分开两类内容：

1. **交付物内容**：最终用户或业务读者应该看到的真实标题、字段、数据、状态、操作、帮助、结论和风险。
2. **交付说明**：实现方式、验证步骤、设计理由、限制、取舍、文件路径、改动摘要和下一步，只放在聊天、PR/MR 或对应专业文档中。

输出前和每次修改后都扫描一次：

- 是否出现 agent 自述、提示词、内部 Skill 名、推理过程、调试记录或下一步计划；
- 是否出现解释页面存在意义的占位文案，而不是产品真实文案；
- 是否把假数据、演示数据或待确认值写成真实结论；
- 是否留下改动痕迹、临时标签、无必要注释或补丁式结构；
- 页面、报告、图和导出结果在脱离聊天上下文后，是否仍像一个真实可用的产品或业务交付物。

命中后先删除或改写，再重新渲染、截图或导出。不能只在聊天里承诺已经过滤。
