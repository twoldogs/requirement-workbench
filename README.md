# 需求全流程工作台 2.3

这是一个给产品经理、研发、测试、实施和售前共用的 Skill 包。拿到一句客户需求、会议纪要、旧 PRD、原型或已有前端后，直接说你要做什么；它会自己判断现在该澄清、写需求、补详细规格、审核、做原型、画交付图，还是检查已有代码。

不用记 Skill 名，也不用先选 PRD、SRS、Impeccable 或 Diagram Design。

## 安装

### Codex

推荐直接克隆仓库并运行安装脚本：

```powershell
git clone https://github.com/twoldogs/requirement-workbench.git
Set-Location -LiteralPath .\requirement-workbench
powershell -ExecutionPolicy Bypass -File .\install-codex.ps1
```

安装脚本会一次安装整个组件组。遇到本机已有同名 Skill，会先移到一个带时间戳的备份目录；全部新文件经过数量和入口校验后才算安装完成。

如果不想使用 Git，也可以在 GitHub 页面点击 `Code -> Download ZIP`，解压后在 PowerShell 中进入目录并运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\install-codex.ps1
```

也可以手工把 `skills` 下的六个文件夹完整复制到 `%USERPROFILE%\.codex\skills`。如果设置了 `CODEX_HOME`，就复制到 `%CODEX_HOME%\skills`。

安装后新开一个 Codex 对话。

### WorkBuddy

下载并上传 [`dist/requirement-workbench-2.3-workbuddy.zip`](dist/requirement-workbench-2.3-workbuddy.zip)。ZIP 内按 `skills/{skill-name}/SKILL.md` 组织，主入口允许自动触发；五个专业组件由工作台内部选择，使用者不需要逐个点名。

## 更新

在仓库目录中拉取最新版，再重新运行安装脚本：

```powershell
git pull --ff-only
powershell -ExecutionPolicy Bypass -File .\install-codex.ps1
```

旧版本会自动备份，更新完成后新开一个 Codex 对话。

## 平时怎么说

像平时交代工作一样说就行：

> 这是客户发来的原话和会议纪要，先帮我理成能讨论的需求。缺关键决策时一次问我一个，并给你建议的答案。

> 把这个需求补成开发和测试能直接用的规格。涉及跨系统同步，把重复、乱序、失败重试和新旧版本组合讲清楚。

> 审一下 PRD 和原型能不能提交。产品经理能处理的、还要查证的、必须请负责人决定的，分开写。

> 这个流程给领导看太绕了，做一张能交付的泳道图。图里的待确认项别替我定。

> 按已经确认的需求做一个可评审原型。原文件别动，在工作副本里做。

> 前端已经有了，检查需求、DESIGN.md、页面状态和交互是否一致。审美建议先别直接改设计规范。

## 它什么时候用哪个组件

| 当前工作 | 自动使用 |
|---|---|
| 原话、纪要、缺陷、旧 PRD 需要整理 | Requirement Workbench 的需求构建模块 |
| 要交给开发测试，字段、状态、规则、异常和验收必须完整 | 详细规格模块 |
| 提交前审核、跨系统/多版本/安全风险 | 深度审核模块 |
| 信息太多、需要一步一步问 | 内置专注表达，不需要点名 `i-have-adhd` |
| 风格、色板、字体、图表或 DESIGN.md 方向没定 | UI/UX Pro Max |
| 落地页、品牌、营销、作品集或转化页面 | Design Taste，负责该页面代码 |
| 后台、工作台、表单、设置、数据界面或已有前端审查 | Impeccable，负责该页面代码 |
| 流程、状态、时序、职责、架构或数据关系需要一张正式图 | Diagram Design |
| 已有原型/代码的动画、过渡、拖拽或微交互需要复核 | 完整 Emil Design Engineering；默认只提问题，由当前代码负责人修改 |

一个页面始终只有一个代码负责人。不同设计 Skill 不会同时改同一路由。

每次交付页面、原型、PDF、PPT、报告、截图、图表或导出文件前，工作台都会再做一次文案过滤：交付物里只留真实产品或业务内容，代理思考、实现理由、调试过程、设计推理和下一步计划留在聊天或评审记录里。修改后还会再过滤一次，不会因为是第二轮调整就跳过。

## 图是怎么进入需求流程的

图不是装饰，也不是新的事实来源。工作台先从需求中确定角色、状态、系统、规则、异常和待确认项，再让 Diagram Design 选择流程图、泳道图、时序图、状态图、架构图等合适形式。

默认交付一个自包含 HTML，里面是内联 SVG。图旁边会补标题、适用范围、阅读提示、关键风险、确认状态和来源。原来的需求正文、验收标准和决策记录仍然保留，不能只剩一张好看的图。

Diagram Design 已替代 Archscribe 成为包内的正式交付图组件。Mermaid 和 draw.io 可以作为导入材料，但会先抽取结构再重画。PNG/SVG 只在明确需要导出时生成；导出才需要 Playwright/Chromium，普通 HTML 图不依赖它。

## DESIGN.md 怎么处理

外部网站的 DESIGN.md、截图和品牌页面只当参考材料。工作台会先提炼可复用原则，去掉对方的品牌名、文案、图片、专有组件名和未经许可的字体/资产，再形成当前项目自己的方向。

项目根目录已有 `DESIGN.md` 时，它是当前视觉实现合同：

- 代码没按合同做：修代码。
- 建议会改变全局设计系统：先说明影响，请产品确认是否修改 `DESIGN.md`，确认后再改代码。
- 功能或可用性确实坏了：按授权处理。
- 只是审美偏好：标成可选建议，不替产品拍板。

## 已有项目不会直接改原件

只读审核不会修改文件。用户要求修改已有 PRD、原型、DESIGN.md 或代码时，工作台先确认源路径和关键入口，保留可恢复基线，再在新的工作目录里修改和验证。只有用户明确要求替换或合并时，才会动源目录。

## 安装后试一句

新开对话后发送：

> 我只有一句需求：想做一个异常处理功能。不要给我 Skill 菜单。先说你理解了什么；如果缺少会改变产品边界的决定，一次只问一个问题，并给出推荐答案。

正常表现是：先说明已知与未核实内容，只问一个最高层关键问题；能先写的内容继续形成草稿，其余标成 `待确认`。如果你补一句“开发测试要直接用”，它会自动深化规格，不会反问你是否需要 SRS。

## 包内内容

- `requirement-workbench`：唯一的全流程入口和路由规则，版本 2.3.0。
- `ui-ux-pro-max`：视觉方向研究库。
- `design-taste-frontend`：品牌和营销页面设计执行。
- `impeccable`：产品界面设计、前端审查与设计系统工具。
- `diagram-design`：正式交付图设计，版本 2.6。
- `emil-design-eng`：完整交互动效工程规则，负责后置专项复核。

第三方来源说明保留在包内，但不会影响实际功能路由。使用时只看当前任务该不该调用、能不能减少真实交付问题。
